# DiscoveryFileSystem: minimal file-system abstraction used by DiscoveryResolver
# (STXT-DISCOVERY-SPEC).
#
# The resolver treats paths as OPAQUE STRINGS: it never parses or concatenates them
# itself, so an implementation may back them with plain OS paths, editor URIs or an
# in-memory tree for tests. All paths returned by an implementation MUST be canonical
# enough that string equality means "same directory".
#
# Platform note: hosts with asynchronous I/O (e.g. JavaScript) implement these
# operations as async; the resolver logic is the same either way.
#
# Symlink note (STXT-DISCOVERY-SPEC §3, §4.1, §4.2, §6, §10): symbolic links are followed
# only where the user chose them.
#  - INSIDE a resolution directory (§3, SHOULD NOT) an implementation over a real file
#    system does not follow them. The recommended way is to OMIT every symlink entry from
#    the listing returned by listDirectory, both directory links and file links: a directory
#    link, if descended into, could lure the recursive descent into a symlink loop or into an
#    unrelated tree; a file link, if loaded as a definition, would read a file from outside
#    the .stxt/ (the levels of the chain include directories the validating party does not
#    control), which could leak that file's content through a resolution error. So a
#    resolution directory loads only the real files it contains.
#  - AT THE PROJECT LEVEL (§4.1, MUST NOT) the `.stxt` entry of an ancestor that is itself a
#    symbolic link forms no level: the resolver asks isSymbolicLink(candidate) during the
#    ascent and skips the candidate when it is a link, whatever it points to. The ancestors
#    are written by whoever created the project — a cloned repository — and a `.stxt -> /`
#    or `.stxt -> $HOME` would make the tool walk that whole tree, parsing every file as a
#    definition and leaking the line that fails to parse.
#  - The USER level, the SYSTEM level and the STXT_PATH entries (§4.2, §6) ARE followed when
#    they are links: the user chooses them, and `$HOME/.stxt` linked to a dotfiles
#    repository is an intended use. The resolver only asks isDirectory there, which follows
#    links.
# The descent is also bounded by DEFAULT_MAX_DESCENT in the resolver, independent of the
# adapter, and listDirectory failures are tolerated per-directory (collectFilesAt), so
# neither a loop nor an unreadable directory can turn resolution into unbounded recursion
# or an escaping exception.

# An entry of a directory listing, as returned by listDirectory().
CLASS DiscoveryEntry
    FIELD path: STRING          # full path, in the same form the file system uses everywhere
    FIELD name: STRING          # base name (last path segment)
    FIELD is_directory: BOOLEAN
END CLASS

INTERFACE DiscoveryFileSystem

    # true if the path exists and is a directory; false otherwise (including I/O errors).
    # Follows symbolic links: a linked user level, system level or STXT_PATH entry is a
    # directory (§4.2, §6).
    FUNCTION isDirectory(path: STRING): BOOLEAN

    # true if the path is a symbolic link — or, on Windows, a junction where the platform
    # tells them apart — whatever it points to and whether or not the target exists; false
    # otherwise (including I/O errors). Only consulted during the project-level ascent
    # (§4.1): the `.stxt` of an ancestor that is itself a link forms no level. A port gives
    # the operation a default that answers false, so an adapter over an abstraction with no
    # links (an in-memory tree, a ZIP) and every adapter written before it keep working.
    FUNCTION isSymbolicLink(path: STRING): BOOLEAN

    # The immediate entries of a directory, in any order.
    FUNCTION listDirectory(path: STRING): DiscoveryEntry[]

    # Reads a file as UTF-8 text. The decode is STRICT (STXT-SPEC §3): input that is not
    # valid UTF-8 MUST be rejected (an I/O-level error, like a missing file), never decoded
    # by silently substituting the invalid sequences with U+FFFD — silent substitution
    # would make two tools see different documents from the same bytes.
    FUNCTION readFile(path: STRING): STRING

    # The parent directory of a path, or NULL when the path is the file-system root.
    FUNCTION parentOf(path: STRING): STRING

    # Joins a directory path and a child name.
    FUNCTION join(path: STRING, name: STRING): STRING

END INTERFACE
